# Verified system repair design

## Objective

Repair the defects reproduced during the repository audit, preserve useful symbolic algorithms, and align advertised capabilities with implemented and tested behavior. User authorization covers planning, code changes, targeted tests, and isolated practical evaluations. It does not cover commits, pushes, publishing, or rewriting the system into an unvalidated neural architecture.

## Design decisions

1. Keep graph reasoning, rational arithmetic, procedural execution, clustering, and quantization. Replace unsafe evaluation and semantic shortcuts where a concrete regression demonstrates incorrect behavior.
2. Restrict Python and command execution by default. Explicit trusted execution must be labeled as trusted, never described as OS isolation. Enforce confirmations and resource controls at the execution boundary. File access always resolves and checks containment.
3. Use consistent positive-edge traversal and conclusion conflict handling. A positive proof opposed by negative evidence is contradictory, rather than route-dependent support/refutation. Preserve documented legacy negative-disjoint behavior until migrated explicitly.
4. Make evidence promotion atomic and idempotent. Preserve source identity, link experiences correctly, and retain inspectable derivations. An analogy remains a hypothesis without independent support.
5. Serialize relations with their exact predicate, polarity, and weights. Keep compatibility with legacy OKF pages without interpreting lossy legacy fields as faithful new-format records. Validate vault paths and reconcile indexes and backlinks.
6. Persist conversation turns before removing full text from active memory. Enforce token and episode bounds, expose realistic memory accounting, and keep retrieval available after eviction.
7. Plans represent every requested subgoal. Unsupported, truncated, empty, malformed, or ungrounded work cannot be reported as complete success. Resolve variable references as tokens.
8. Treat canonical AST generation as a bounded capability. Reject additional unsupported constraints and replace misleading general-synthesis claims. Keep a trainable linear router, expose its actual architecture, and implement explicit checkpoint/feedback contracts rather than claim implicit learning.
9. Separate packaged immutable resources from mutable runtime state. Runtime configuration is injected consistently, supports source and installed execution, and does not share mutable vaults accidentally.
10. Evaluation compares each expected result, uses independent negative examples, separates performance from correctness, and never substitutes invented provider/model results.

## Compatibility and validation

Regression tests precede each implementation batch. Existing tests that assert unsafe execution, fixed overconfident conclusions, fabricated search records, unsupported generalization, or mandatory native acceleration are updated only alongside explicit behavior-contract changes. Public status strings and CLI syntax remain stable where possible; intentional changes are documented. No new dependency is added without evidence it is necessary.

Each batch has unit regressions, related existing tests, and an isolated practical scenario. Final validation covers affected subsystems, an installed-resource smoke check when local build tooling is available, Python/native parity, persistence reopening, and truthful evaluation output. Tests use temporary databases and vaults; no test writes the project's live knowledge store.

## Completion criteria

Every audit concern maps to a tracked task and evidence. Completed tasks list the exact successful checks; unresolved design limitations stay visible. Regex counts and conditional counts are descriptive metrics, not a goal to reduce blindly. No claim of general neural understanding, universal factual correctness, or OS-level sandboxing is made without corresponding implementation and evidence.
